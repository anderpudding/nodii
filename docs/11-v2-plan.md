# Nodii v2 계획 — iOS 앱

> 버전 0.2 · 2026-10-09 · 근거: `01-requirements.md`, `02-system-design.md` §12, `design/mobile-screens.md`
> v0.2 변경: 디자인 완료 반영, 푸시를 v3(커뮤니티)로 확정, 로드맵 v2→v2.1→v3 추가, M2 분할, i18n 제안, 커뮤니티 대비 메모(§7)

## 1. 왜 iOS인가

v1을 만든 이유가 "모바일과 PC가 연동되는 투두 앱"이었고, 데스크톱만으로는 그 절반입니다. 아침에 폰에서 체크하고 책상에서 맥으로 이어 쓰는 게 원래 목표였습니다.

설계도 이걸 전제로 깔아 뒀고, 실제로 확인했습니다.

- `packages/core`(도메인 로직)와 `packages/api`(Supabase 접근·실시간)에 **브라우저 전용 API가 하나도 없습니다.** `window`·`document`·`localStorage`·`navigator`를 쓰는 곳이 없어서 React Native에서 그대로 돌아갑니다.
- 세션 저장소는 `AuthStorage` 인터페이스로 주입받습니다. 모바일은 **SecureStore** 어댑터만 새로 씁니다.
- 로그인이 이메일 6자리 코드라 **딥링크 처리가 필요 없습니다.**
- DB 스키마·RLS·RPC는 그대로 씁니다. 서버 변경 없이 클라이언트만 추가하는 게 NFR-09였고, 이번에 그걸 실제로 확인하는 셈입니다.

**방식:** Expo (React Native). **디자인:** `design/mobile-screens.md` 완료, 토큰은 데스크톱과 공유.

## 3. 단계 (주 15~20시간 기준, 약 9~10주)

| 단계 | 내용 | 기간 | 완료 기준 | 디자인 |
|---|---|---|---|---|
| M0 | Expo 앱을 모노레포에 넣고 core·api 재사용 확인, EAS 빌드 → **TestFlight 설치까지 한 번** | ~1주 | 실기기에서 화면이 뜨고 Supabase 헬스 체크·SecureStore 읽기/쓰기 성공 | — |
| M1 | 인증 + 앱 셸 (OTP 6칸, 세션 유지, 최소 버전 게이트, 내비게이션 뼈대, 키보드 회피) | ~1주 | 새 계정 가입 → 재실행 시 로그인 유지 → 로그아웃 | `MobileLogin`, §1 공통 규칙 |
| M2a | 오늘 화면 + 빠른 추가 (주간 스트립, 목표별 목록, 추가 시트, 연속 입력) | ~1.5주 | 폰에서 하루를 기록할 수 있다 | `MobileToday`, `MobileAdd` |
| M2b | 제스처 묶음 (밀기 완료·옮기기·삭제, 길게 누르기 메뉴, 실행 취소 토스트) | ~1주 | 밀기로 되는 일이 모두 길게 누르기에도 있다 | `MobileGestures`, `MobileMenu`, `MobileUndo` |
| M3 | 월간 펼침 + 날짜 이동 + 하루 메뉴 | ~1.5주 | 날짜를 옮기고 지난 할 일을 가져올 수 있다 | `MobileMonth` + 날짜 시트(그려야 함) |
| M4 | 루틴 (목록·완료·건너뛰기·편집·적용 범위) | ~1.5주 | 맥에서 만든 루틴이 폰의 같은 날짜에 보인다 | `MobileRoutines`, `MobileRoutineEdit` + 범위 시트(그려야 함) |
| M5 | 실시간 동기화 + 오프라인 읽기 + 설정(계정 삭제 포함) | ~1주 | **맥과 폰을 나란히 놓고 한쪽 변경이 몇 초 안에 반영** | `MobileSettings` + 오프라인 표시(그려야 함) |
| M6 | iOS 출시 준비 (App Store Connect, 스크린샷, 심사 노트, TestFlight 베타) | ~1~2주 + 심사 | 심사 통과 | — |

M0가 가장 중요합니다. v1에서 배포 스파이크를 0단계에 둔 것과 같은 이유로, 가장 불확실한 것(Expo 빌드가 실기기까지 가는가)을 먼저 끝냅니다.

**M2를 둘로 나눈 이유:** 디자인 문서의 M2에 화면이 다섯 개(`MobileToday`·`MobileAdd`·`MobileMenu`·`MobileGestures`·`MobileUndo`) 있습니다. 제스처는 데스크톱에 없던 코드라 검증도 새로 해야 해서, 한 단계에 묶으면 v1의 3단계처럼 커집니다.

**각 단계 시작 전에 그려야 하는 화면**이 디자인 문서 §3에 여섯 개 남아 있습니다. 해당 단계 지시서를 쓰기 전에 그리면 됩니다.

## 4. 재사용과 공유 전략

- `packages/core`: 그대로. 수정이 필요하면 데스크톱 테스트가 먼저 깨지니 안전합니다.
- `packages/api`: 그대로. repository·훅·낙관적 업데이트·실시간 구독을 공유합니다. 다른 곳은 두 군데뿐입니다.
  - `AuthStorage` → SecureStore 어댑터 (M1)
  - 캐시 영속화 저장소 → AsyncStorage 또는 MMKV (M5)
- 공유하지 않는 것: 화면, 스타일, 제스처, 내비게이션. **UI는 공유하지 않습니다.**
- 토큰은 공유합니다. 간격·터치 타깃·글자 크기는 모바일 값(디자인 문서 §1).

## 5. 리스크

| 리스크 | 대응 |
|---|---|
| Expo SDK의 React 버전이 `packages/api`의 peer와 안 맞을 수 있음 | M0에서 가장 먼저 확인. 안 맞으면 SDK를 맞추거나 peer 범위를 넓힌다 |
| iOS 심사가 더 까다로움 | `10-app-review-response.md`를 iOS용으로 고쳐 재사용. 계정 삭제가 이미 앱 안에 있음 |
| 실사용자가 늘면 Supabase 무료 플랜 한도 | 월 1회 MAU·DB 확인, 80%에서 Pro 검토 (NFR-11) |
| 제스처 구현이 접근성 설정과 충돌 | 밀기로 되는 일은 반드시 길게 누르기에도 둔다 (디자인 문서 §1) |
| 데스크톱 유지보수와 병행 | 데스크톱 버그는 별도 짧은 브랜치로. 모바일 단계에 섞지 않는다 |

## 6. 제안 (검토용)

### 6.1 i18n 기반을 v2에 같이 깔기 — 권장

지금 사용자 문구는 두 앱에 하드코딩된 한국어입니다. 모바일을 만들면 같은 문구가 양쪽에 흩어지고, 나중에 영어를 넣을 때 추출 비용이 두 배가 됩니다. 커뮤니티로 사용자를 늘릴 계획이면 영어는 언젠가 필요합니다.

- M1~M2a에 메시지 카탈로그를 도입하고 **한국어만 채웁니다.** 영어 번역은 나중에.
- `core`가 이미 오류를 `'weekday_required'` 같은 코드값으로 돌려주는 구조라 유리합니다.
- 비용: 초기 반나절 + 문구를 쓸 때마다 카탈로그 경유. 나중에 하면 며칠.

### 6.2 로컬 리마인더를 v2.1로 분리 — 권장

"오전 9시에 오늘 할 일 알려주기", "루틴 시간 알림"은 `expo-notifications`의 로컬 스케줄링만으로 됩니다. 서버 함수·토큰 저장·푸시 인증서가 필요 없습니다. 폰 앱에서 체감이 큰 기능이라, 서버 푸시(v3)를 기다리지 않고 작게 넣을 수 있습니다.

### 6.3 로드맵

| 버전 | 내용 |
|---|---|
| **v2** | iOS 앱 (기능 패리티) + i18n 기반 |
| **v2.1** | 로컬 리마인더 · 데스크톱 Could 항목 · 오프라인 쓰기 중 **하나**를 골라 짧게 |
| **v3** | 커뮤니티 (프로필·친구·공개 범위) + 서버 푸시 |

## 7. v3 커뮤니티를 위해 지금 알아 둘 것

프로필·친구 추가·친구의 투두 보기·목표별 공개 범위는 지금까지의 변경과 **성격이 다릅니다.** v1~v2는 "내 데이터만 다루는 앱"이라 RLS가 `user_id = auth.uid()` 한 줄이었습니다. 커뮤니티는 그 전제를 바꿉니다. 미리 정해 둘 필요는 없지만, 알고 있어야 할 것들입니다.

1. **App Store 요건이 달라집니다.** 사용자 간에 보이는 콘텐츠가 생기면 Guideline 1.2(UGC)에 따라 **신고·차단**이 사실상 필수입니다. 지금 심사 답장에 "no content shared between users"라고 쓴 부분도 그때는 바뀝니다. 이용약관과 개인정보 라벨도 함께 개정해야 합니다. 친구 기능을 넣는 버전은 **심사가 처음처럼 까다로울 것**으로 보고 일정을 잡는 게 좋습니다.
2. **RLS가 복잡해집니다.** "내 것" + "친구가 나에게 공개한 것"을 함께 허용해야 합니다. 1단계에서 만든 pgTAP 테스트가 여기서 제일 큰 자산이 됩니다. 정책을 고칠 때마다 "A가 B의 비공개 목표를 볼 수 없다"를 테스트로 못 박아야 합니다.
3. **친구 찾기는 핸들로.** 이메일 검색은 "이 주소가 Nodii를 쓰는지" 알려주는 셈이라 프라이버시 문제가 됩니다. `@handle` + 초대 링크를 권합니다. 핸들은 전역 유니크라 선점·변경 정책이 필요합니다.
4. **공개 범위는 목표 단위가 맞습니다.** 이미 목표가 색·보관의 단위이고 할 일은 반드시 목표에 속합니다(GOAL-07). `goals.visibility`(비공개/친구공개) 한 컬럼이면 자연스럽게 얹힙니다. 기본값은 비공개, 과거 기록 공개 여부는 따로 정합니다.
5. **지금 스키마를 미리 넣지는 마세요.** 쓰지 않는 컬럼과 테이블은 부채입니다. v3 설계 때 한 번에 넣는 게 낫습니다.
6. **비용.** 친구 피드는 읽기가 크게 늘어납니다. v3 전에 Supabase Pro 전환을 전제로 보는 게 안전합니다.
