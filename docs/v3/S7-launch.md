# S7 — 출시 준비 (약관 · 라벨 · 심사 · 운영 적용 · 공개)

> 기준: `docs/16-v3-social-plan.md` §6·§7·§8 S7, SOC-60~63, D33(이 지시서에서 정함), `docs/05-release-runbook.md`(macOS), `docs/13-ios-release-runbook.md`(iOS), S0~S6 지시서의 "사람이 확인" 항목.
> 이 단계는 **Codex 작업(A)** 과 **사람 작업(B)** 으로 나뉩니다. Codex는 A만 하고, B는 문서로만 정리합니다.
> 브랜치: `release/v3` (A). 원격·운영 Supabase, App Store Connect, 빌드 업로드는 사람이 합니다.

## 0. 목표와 순서

**완료 기준: 두 앱(iOS·macOS) v3가 심사를 통과해 같은 날 공개되고, 운영에서 소셜이 켜지며, 예전 앱 버전은 업데이트 안내로 막힌다.**

전체 순서(사람 기준, 자세한 내용은 §B):

1. **A — Codex**: 약관·개인정보처리방침 개정 초안, 앱 안 약관 동의 문구, 버전 0.3.0, 심사 데모 데이터 스크립트, 런북·심사 답장 문서 갱신(§A).
2. **B1 스테이징 확인의 날**: 스파이크(또는 스테이징) 프로젝트에서 S3~S6의 실기기 확인을 한 번에.
3. **B2 운영 적용**: Supabase Free 유지 + 매일 암호화 백업(D34), 마이그레이션, Edge Function 2개, 비밀 값, Vault, Data API 노출 스키마 확인.
4. **B3 심사 제출**: 두 앱 빌드·업로드, 개인정보 라벨, 연령 등급, 심사 노트·데모 계정, **수동 출시**로 제출.
5. **B4 출시의 날**: 두 앱 승인 뒤 같은 날 출시 → 최소 지원 버전 올리기 → 확인.
6. **B5 출시 후 2주**: 신고 매일 확인, 함수 로그·푸시 오류 확인.

### D33 — `social_enabled`는 심사 제출 전에 운영에서 켠다 (계획서 §6 "심사 통과 뒤 켠다"를 바꿈)

- 심사 팀이 소셜 기능을 보려면 운영 DB의 플래그가 켜져 있어야 합니다.
- 켜도 **예전 앱(0.2.x)에는 소셜 화면이 없으므로** 공개 사용자에게 바뀌는 것이 없습니다. 새 앱은 "수동 출시"로 두므로 승인 전후에도 공개되지 않습니다.
- 예전 앱의 조회 누수(계획서 §6 "기존 버전 앱")는 소셜 관계가 생겨야 나타나는데, 관계는 새 앱으로만 만들 수 있습니다. 출시 날 최소 지원 버전을 올려 막습니다.
- 서버는 플래그를 검사하지 않으므로(S1) API를 직접 부르는 사람은 플래그와 상관없이 소셜 테이블을 쓸 수 있습니다. 이것은 마이그레이션을 운영에 적용한 순간부터 같습니다 — 적용을 심사 제출 직전으로 미뤄 그 기간을 줄입니다.

## A. Codex 작업 (브랜치 `release/v3`)

### A1. 약관·개인정보처리방침 개정 초안 (`site/terms.html`, `site/privacy.html`, 영어)

초안입니다. 법률 검토 표시(`[[REVIEW: …]]`)를 남겨 사람이 확인하게 합니다. 기존 문체·구조를 따르고 날짜는 `[[TODO: effective date]]`.

- **Terms** — App Store 가이드라인 1.2(사용자 생성 콘텐츠)에 필요한 항목:
  - 공개되는 콘텐츠: 닉네임, ID, 소개, 프로필 사진, 공개 범위를 정한 목표의 할 일·루틴과 완료 기록, 반응.
  - **불쾌한 콘텐츠와 괴롭히는 사용자에 대한 무관용**(zero tolerance) 문장, 금지 행위(스팸·사칭·괴롭힘·불법·성적 콘텐츠 등).
  - 신고·차단 방법, **신고는 48시간 안에 검토**(2026-11-15 결정, 이의 제기는 지원 메일)하고 콘텐츠 숨김·초기화·소셜 이용 정지로 조치할 수 있음.
  - 사용자가 올린 콘텐츠의 권리와 Nodii가 서비스 제공을 위해 보여 주는 범위의 이용 허락.
  - 연락처(지원 메일).
- **Privacy** — 새로 처리하는 데이터와 목적·보관:
  - 소셜 프로필(닉네임·ID·소개·사진), 초대 토큰, 팔로우·차단 관계, 반응, 알림, 알림 설정, 푸시 토큰(기기 언어·시간대·앱 버전), 신고(사유·상세).
  - 다른 사용자에게 보이는 것(공개 범위별), 차단·정지 시 숨김.
  - 보관: 바꾼 ID는 30일간 묶음, 계정 삭제 시 모두 삭제(사진 포함), 신고 기록은 `[[REVIEW: 보관 기간]]`.
  - 처리자 추가: **Resend**(신고 알림 메일), **Expo**(푸시 전달) 및 Apple Push Notification service. 기존 Supabase 항목 유지.
  - 푸시 알림은 선택이며 기기 설정에서 끌 수 있음. 사진은 메타데이터(EXIF 위치 등)를 지운 뒤 저장.
- `site/support.html`(영어·`ko/`): 신고·차단 방법, 계정 정지 문의 안내 한 단락.
- `grep -n "TODO\|REVIEW" site/*.html` 목록을 보고에 붙입니다.

### A2. 앱 안 약관 동의 문구 (SOC-63, 가이드라인 1.2)

- 프로필 만들기 화면(S2 `ProfileSetupH1`/`MacProfileSetupH1`)의 [시작하기] 위에 12~13 `muted` 한 줄: "시작하면 이용약관과 커뮤니티 규칙에 동의하게 돼요." — "이용약관"은 링크(`VITE_TERMS_URL`/iOS 같은 값, 기존 설정 화면의 약관 링크와 같은 출처). 체크박스는 두지 않습니다.
- 한국어·영어 카탈로그. 테스트: 링크가 약관 주소를 연다.
- 다른 화면·흐름은 바꾸지 않습니다.

### A3. 버전 0.3.0

- `bash scripts/bump-version.sh 0.3.0 --platform all`(같은 표시 번호 정책). iOS 빌드 번호는 EAS 원격 자동 증가 그대로, macOS 빌드 번호는 기존 방식.
- 태그는 만들지 않습니다(사람이 B3에서).

### A4. 심사 데모 데이터 스크립트 (`supabase/snippets/review-demo-setup.sql`)

사람이 운영 Studio에서 **두 데모 계정을 Auth에서 만든 뒤** 실행합니다. UUID는 맨 위 변수 두 개(`[[TODO]]`)에만 넣게 합니다.

- 두 계정: 기존 `appreview@nodii.app`(A)과 새 `appreview2@nodii.app`(B). 둘 다 소셜 프로필(닉네임·ID·소개, 사진 없음).
- **서로 팔로우**(맞팔). B의 목표 셋: 팔로워 공개·맞팔 공개·나만. 각 목표에 오늘·어제 할 일 몇 개(일부 완료)와 매일 루틴 하나(오늘 완료).
- A가 B의 완료 항목 하나에 좋아요, B가 A를 팔로우한 알림, A의 친구 완료 알림 켜기(전체).
- 다시 실행해도 같은 결과(먼저 두 계정의 소셜 데이터를 지우고 다시 만듦 — 단, `auth.users`와 기존 v2 데이터는 건드리지 않음). 실행 결과 확인용 `select` 몇 줄.
- 로컬에서 `pnpm db:reset` 후 두 테스트 계정으로 돌려 보고, 앱에서 A로 로그인하면 아바타 줄·친구 하루·알림이 보이는지 확인합니다.

### A5. 문서 갱신

- `docs/10-app-review-response.md`: "no content shared between users" 문장을 v3 내용으로 바꿉니다(사용자 간 공유가 생김, 신고·차단·무관용 약관, 24시간 검토, 데모 계정 두 개).
- `docs/05-release-runbook.md`(macOS)·`docs/13-ios-release-runbook.md`(iOS)에 **v3 절**을 더합니다: §B2 운영 적용, 개인정보 라벨 표(§B3), 연령 등급, 심사 노트 영어 초안(§B3), 출시 날 순서(§B4). 기존 내용은 지우지 않습니다.
- `docs/v3/README.md` 진행 기록, 이 지시서의 §B 체크박스는 그대로 두고 A의 결과만 기록합니다.

### A6. 확인

- `pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm test`(기본 병렬, 시간 제한·워커 수 그대로), `pnpm db:reset` → `pnpm db:test`, 데모 스크립트 로컬 실행.
- 하지 말 것: 스키마·RLS·Edge Function 변경, 원격·운영 Supabase 접속, 태그·업로드, 법률 문구를 확정된 것처럼 쓰기(검토 표시 유지). 커밋 메시지는 영어, trailer 없이.
- 보고: 바뀐 파일, 남은 `TODO`·`REVIEW` 목록, 데모 스크립트 로컬 결과.

## B. 사람 작업

### B1. 스테이징 확인의 날 (스파이크 `nodii-spike` 또는 새 스테이징 프로젝트)

준비: 최신 main의 마이그레이션 적용, `report-profile`·`send-push` 배포, `RESEND_API_KEY`·`REPORT_INBOX`·`PUSH_WEBHOOK_SECRET`(+`EXPO_ACCESS_TOKEN`) 설정, Vault `project_url`·`push_webhook_secret`, `social_enabled = true`. 두 앱을 이 프로젝트로 빌드(TestFlight 내부 테스트 / 서명한 macOS 앱). 계정 셋 이상.

- [ ] **macOS 서명 빌드 실행**: Associated Domains가 들어간 프로비저닝 프로필로 서명한 앱이 정상 실행된다(`rustc` 1.90 이상).
- [ ] **S3** HTTPS 초대 링크 `https://nodii.app/u/<token>`이 iPhone·macOS에서 앱이 꺼져 있을 때·켜져 있을 때 모두 다른 사람 프로필로 열린다.
- [ ] **S3** 신고하면 지원 메일함에 메일이 온다(제목 `[Nodii report] …`).
- [ ] **S4** 다른 기기에서 바꾼 공개 범위·"오늘에 보일 사람" 순서가 앱을 앞으로 가져오면 맞춰진다. iOS 사람 하루 머리가 스크롤로 접히고, 동작 줄이기에서는 바로 바뀐다. 끌어서 순서 바꾸기·VoiceOver 위/아래 옮기기.
- [ ] **S5** iPhone과 Mac 사이에서 하트·새 팔로워·친구 완료 알림이 실시간으로 뜬다.
- [ ] **S6** 앱을 완전히 종료한 iPhone에 좋아요 푸시가 오고 누르면 그날 오늘 탭. 같은 친구 완료는 3시간에 한 번. 기기 시간 밤 11시 이후 안 옴. macOS 첫 알림 권한 창, 알림 끈 상태, 알림 클릭 이동. 배지가 어디에도 없음.
- [ ] 소셜 꺼짐(`social_enabled = false`)으로 바꾸면 두 앱이 v2 화면으로 돌아간다. 다시 켠다.
- 문제가 있으면 그 단계 지시서로 Codex에 수정을 맡기고, 이 줄부터 다시.

### B2. 운영 적용 (심사 제출 직전, `nodii`)

1. [ ] **Free 유지 + 매일 암호화 백업**(D34): `docs/05-release-runbook.md` §8 "DB 백업"대로 age 키·R2 버킷·GitHub Secrets를 만들고 `DB backup` 워크플로를 수동 실행 → R2에 파일이 생기고, 복호화한 파일로 로컬 DB 복원까지 한 번 확인.
   - Pro로 바꾸는 기준: DB 350MB, 파일 700MB, 동시 Realtime 연결 150개 중 하나에 닿을 때(월 $25).
2. [ ] Data API 노출 스키마에 `net`·`vault`·`social_private`이 **없음**을 확인.
3. [ ] `supabase db push`로 마이그레이션 적용 → `select count(*) from public.social_profiles;`(0), RLS 켜짐 확인.
4. [ ] `supabase secrets set RESEND_API_KEY=… REPORT_INBOX=… PUSH_WEBHOOK_SECRET=…`(+`EXPO_ACCESS_TOKEN`).
5. [ ] `supabase functions deploy report-profile` · `supabase functions deploy send-push`.
6. [ ] Vault에 `project_url`(운영 URL)·`push_webhook_secret`(4와 같은 값). **함수 배포 뒤에** 넣습니다.
7. [ ] Storage `avatars` 버킷 정책 확인(S1).
8. [ ] Studio 저장 쿼리 `reports-open`·`reports-resolve` 등록(`supabase/snippets/`).
9. [ ] Auth에서 `appreview2@nodii.app` 만들기(비밀번호 관리자에만 저장) → 두 계정으로 앱에서 한 번씩 로그인해 프로필 만들기 → `review-demo-setup.sql` 실행.
10. [ ] `update public.app_config set value = 'true' where key = 'social_enabled';`(D33).
11. [ ] 운영에서 두 데모 계정으로 신고 한 번 → 메일 수신 → `reports-resolve`로 정리.

### B3. 심사 제출 (두 앱, 수동 출시)

- [ ] 빌드: iOS `eas build --profile production` → TestFlight 처리 확인 → 개발에 안 쓴 기기에서 설치·로그인·소셜 한 바퀴. macOS `v0.3.0` 태그 → `release.yml` 빌드·업로드(05 런북).
- [ ] **개인정보 라벨**(두 플랫폼 공통, 추적 모두 "아니요", 모두 "앱 기능"·"사용자와 연결"):

  | 데이터 유형 | 새로/기존 | 근거 |
  | --- | --- | --- |
  | 연락처 정보 → 이메일 주소 | 기존 | 로그인 |
  | 사용자 콘텐츠 → 기타 사용자 콘텐츠 | 기존(범위 넓어짐) | 목표·할 일·루틴, 소개, 반응, 신고 |
  | 사용자 콘텐츠 → **사진 또는 비디오** | 새로 | 프로필 사진 |
  | 식별자 → **사용자 ID** | 새로 | 공개 ID(핸들)·닉네임 |

  - [ ] 결정 필요: 푸시 토큰을 "식별자 → 기기 ID"로 신고할지. 제안: 신고하지 않음(광고·추적 식별자가 아니고 Apple 정의의 기기 ID와 다름). 확신이 없으면 신고하는 쪽이 안전합니다.
- [ ] **연령 등급** 설문 다시 답하기: 사용자 생성 콘텐츠 "예", 사용자 간 메시지·채팅 "아니요"(댓글·DM 없음, D11). 나온 등급을 기록.
- [ ] **심사 노트**(영어, A5 초안): 두 계정과 비밀번호, 두 계정이 맞팔이고 데이터가 들어 있음, 확인 경로(오늘 탭 위 아바타 줄 → 친구 하루 → 하트 / 알림 탭 / 프로필 → 다른 사람 프로필 `⋯` → 신고·차단 / 설정 → 차단한 사람), 신고는 24시간 안에 검토, 약관 URL.
- [ ] 버전 정보·스크린샷(소셜 화면 1~2장 추가)·영어/한국어 설명 갱신.
- [ ] 출시 방식 **"이 버전을 수동으로 출시"** 로 두고 두 앱 제출.
- [ ] 거절되면 `10-app-review-response.md`와 런북 §거절 대응. 1.2 관련이면 약관·신고·차단 경로를 영상으로 보여 줍니다.

### B4. 출시의 날 (두 앱 모두 승인된 뒤, 같은 날)

1. [ ] 두 앱 **동시에 출시**(App Store Connect → 이 버전 출시). 스토어에서 0.3.0을 받을 수 있는지 확인.
2. [ ] 최소 지원 버전 올리기(계획서 §6 — 예전 앱의 친구 데이터 섞임 방지):
   ```sql
   update public.app_config set value = '0.3.0' where key in ('min_ios_app_version', 'min_macos_app_version');
   ```
